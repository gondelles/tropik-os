## Purpose

Define the complete public information architecture for Re:Build, the relationships between pages, minimum page scope, navigation rules, page templates and design criteria for future WordPress / WooCommerce implementation.

This document is the current sitemap reference for all Re:Build page generation. It does not authorize publication or unsupported claims.

---

# 1. Information-architecture principle

The website must NOT mirror the business-plan/thesis chapter structure.

The public experience is organized around user questions:

1. What happened / what problem exists?
2. What is Re:Build doing?
3. How does the process work?
4. What materials/products come out?
5. Where can those products be used?
6. What impact is being created?
7. How can I support / partner / buy?
8. What evidence supports the claims?

Every page answers one primary question and then routes the visitor to the next logical page.

# 5. Page relationships

## Core relationship rules

1. Every Recovery page links to the relevant Process page.
2. Every Process page links to the materials produced by that process.
3. Every Material page links to its manufacturing process and approved/potential application pages.
4. Every Rebuilding/Application page links back to suitable products and testing/status.
5. Every Impact metric links to Methodology / Evidence.
6. Every Support claim about use of funds links to Transparency.
7. Every Update links to at least one permanent evergreen page.
8. Every experimental/R&D product links to its limitations/testing status.
9. No unsupported claim should exist without a visible evidence/status path.

# 8. Design criteria

## Overall direction

Re:Build should feel:
- credible;
- human;
- practical;
- documentary;
- technically competent;
- constructive;
- optimistic without minimizing disaster impact.

Do not use disaster spectacle, victim imagery, poverty aesthetics or political propaganda as visual devices.

## Visual hierarchy

Prefer:
- strong typography;
- whitespace;
- simple grids;
- documentary field photography where consent/rights exist;
- diagrams/process flows;
- restrained metric cards;
- material texture/detail photography;
- maps when useful;
- clear status badges;
- cards for related pages.

Avoid:
- giant walls of copy;
- excessive gradients;
- gimmicky animations;
- generic eco stock photography;
- overuse of green color as shorthand for sustainability;
- pseudo-scientific diagrams;
- unsupported counters.

## Content density

- One primary message per screen/section.
- Paragraphs generally short.
- Use expandable detail / FAQs for technical depth.
- Use tables only when comparison materially improves understanding.
- Keep evidence close to the claim it supports.

## Navigation

- Sticky or consistently accessible primary navigation.
- Breadcrumbs on deep pages.
- Clear Previous / Next journey navigation.
- Related-content cards at bottom.
- Mobile-first menu must remain simple.

## Brand system

Use approved Tropik / Re:Build design tokens where they exist. Do not create a new unrelated design system inside Re:Build without founder approval.

## Accessibility

- sufficient contrast;
- semantic headings;
- keyboard-accessible controls;
- alt text;
- readable mobile body type;
- no critical information communicated only by color.

# 11. Build rule for Claude / implementation agents

Before creating or editing any Re:Build page:

1. Read this sitemap.
2. Identify the page's primary question.
3. Use the correct standard page template.
4. Keep only content necessary to answer that question.
5. Add links to previous/next/related pages.
6. Preserve claim/status classifications.
7. Do not invent facts, performance data, partners, funding or product certifications.
8. Prefer reusable WordPress patterns/components.
9. Keep implementation mobile-first and WooCommerce-compatible.
10. Do not redesign the wider Tropik brand/theme unless explicitly authorized.
